## Completed execution checks

The NVHPC heap test checked 1,048,576 doubles after 128 increments and obtained the exact expected sum, with CUDA managed-memory allocation confirmed. A separate stdpar test wrote 262,144 nonuniform values into `cudaMalloc` device-only output and verified every copied-back value. That allocation reported device type and no host pointer. All synchronization, copy and cleanup calls succeeded. These standalone tests establish compiler GPU execution; the framework and cavity checks below provide separate OpenFOAM evidence.

SPUMA's own executor wrote all 65,536 runtime-seeded results exactly into verified device-only output, using its normal 1 GiB managed fixed-pool startup. Its double reduction and every CUDA status/synchronization check passed. A later, distinct preregistered strict cavity completed five steps through 0.025 s with actual solver-child and Allrun exit codes zero. Peak all-corrector local continuity was 8.770776844746355e-9; independent final saved-flux imbalance was 6.921170270841277e-9. Inside its complete first-step range, the exact child thread produced 2,445 successful observed launch API calls and 2,445 successful device synchronizations, with no failures and a successful synchronization after the last launch.

The reviewed [SPUMA source, recipes and functional evidence](spuma/README.md) include exact case inputs, saved fields, logs, gates, source/rules, scoped build fixes and a lossless restricted API/NVTX/process trace subset. Full raw profiler reports and environment metadata remain private. The original longer SPUMA fixture failed its all-corrector screen and was intentionally stopped after 12 completed steps, with actual child exit -15; it remains a separate failed record. The strict fixture's tighter pressure `relTol=0` and shorter horizon were preregistered, and its pass does not replace that original failure or establish rotor validity, CPU equivalence or speedup.

The native OpenCFD framework separately passed its actual 32,768-element scalar/vector field arithmetic test using the CUDA Umpire managed pool: zero mismatches, exact scalar/dot sums, managed allocation type confirmed and successful synchronization. Nsight recorded eight successful CUDA launch API calls inside the annotated algebra window, with no failed launches or synchronization calls. This arithmetic gate is separate from the later CFD cavity test.

The native same-branch CPU and stdpar GPU strict cavities both completed their preregistered five steps through 0.025 s, passing saved-field, flux, continuity and actual-child exit gates. Peak all-corrector continuity was about 1.078e-8 on each backend. Maximum relative L2 field differences were 3.71e-15 for U and 1.30e-13 for p. The GPU's complete first step had 12 successful observed launch API calls and 13 successful synchronizations, with no failures and successful device synchronization after the last launch. The original longer CPU and GPU fixtures failed their all-corrector screens with the loose first-pressure `relTol=0.05`; those failures remain distinct from the tighter, shorter strict passes. API calls are not unique kernels or a kernel-activity timeline.

The native `ListPolicy` enables offload only at lengths of at least 1,000. The strict 400-cell cavity has 760 internal faces, so its flux interpolation ran on CPU even though other operations made the 12 genuine first-step CUDA launch calls. That short test therefore does not validate the GPU flux-interpolation path or rotor support.

The larger native stdpar C29 mesh has 2,739,208 internal faces. The original 2.2 application aborted with `cudaErrorIllegalAddress` while constructing starting face flux, before any source evaluation, controller update or time step. That failure remains preserved. A separate controlled test isolated a descriptor-storage failure class: managed raw arrays and a managed-heap descriptor passed at 4,096 entries, while the same binary's reference-captured stack descriptor aborted on the offloaded path; its sequential 400-entry control passed. Compute Sanitizer disabled itself because CUDA initialized first, so it supplied no valid fault-address or kernel attribution.

The separately reviewed 2.3 variant gives 16 application field/matrix descriptors managed heap ownership without changing the C29 source mathematics. Its full 922,576-cell GPU initialization completes normally. Computed velocity and pressure match the reference exactly; computed starting flux differed by 3.1742559698354905e-19, which still failed the preregistered exactness test. The planned common-phi fallback then supplied byte-identical Foundation14 starting flux to both native backends. All starting velocity, pressure and flux values match exactly. This successful initialization does not by itself qualify the GPU time loop.

A distinct, preregistered strict-pressure protocol sets the first pressure relative tolerance to zero at the unchanged absolute tolerance. The original loose-pressure five-step continuity failures remain unwaived. New Foundation14 and native CPU controls each completed five fixed steps normally with unchanged source/mesh/starting fields, verified actual solver/library identities, and all **499** frozen numerical/source/continuity checks passing.

The actual 2.3 GPU functional profile then failed with true waited solver exit **-11 (SIGSEGV)** and separate profiler exit 139. It printed Time 0.6001 but no Courant diagnostic result, source evaluation, controller update, completed step or End marker. Its original case files and actually observed declared libraries remain unchanged, and the owned solver was reaped. This narrows the failure interval to the initial Courant diagnostic or adjacent operations; the exact instruction and device-kernel cause remain unproven.

A subsequent fresh-case test used the **same binary and libraries without profiling, observer or debugger injection**. It also returned -11 after Time 0.6001, with zero completed steps/source/controller calls. All original inputs and loaded-library hashes remained unchanged. Its three initial audit files exactly match the qualified shared-startup files. The crash therefore reproduces without Nsight. There is no accepted full-step CUDA proof, GPU rotor result, native CPU/GPU transient parity or speedup. A conservative 2.4 heap-ownership proposal passed static review but was not built: the available source evidence does not establish it as a fix.

The reviewed [native installation source and evidence](native_installation/README.md) preserve the base installation, current versus historical core identities, strict small-cavity results and earlier large-case diagnostics. Newer C29 source and runtime outcomes are provided separately below. Historical workstation recipes need deliberate fresh-tree adaptation; no fresh-host rebuild was tested.

That [C29 source, saved-field and runtime addendum](c29_managed_strict/README.md) is now included. A later offline reproduction test restored **91 exact files** and replayed **all 499 checks with zero failures**, exactly matching every original check record. Both Python children exited zero; package, seed and restored files stayed unchanged. This tests delivery reproducibility without running CFD, and does not qualify either failed GPU transient.

The native core's generated CUDA registration stub initially used GCC's small-PIC model and exceeded its ARM64 GOT range. A command-scoped wrapper changed only that stub compilation from `-fpic` to `-fPIC`; the core shared library linked successfully with all 628 compiled objects unchanged. This private build workaround does not modify the shared SDK or system compiler. A [similar upstream report](https://forums.developer.nvidia.com/t/error-while-compiling-on-thea-gh-node/335300) describes the same class of failure; [GCC documents the PIC distinction](https://gcc.gnu.org/onlinedocs/gcc/Code-Gen-Options.html).

AmgX solved a 32³ manufactured Poisson system with an independently computed relative L2 residual of about 7.3×10⁻¹¹. Its solve phase produced 1,316 successful intercepted CUDA launch API calls. The Foundation 14 cavity comparison then completed 20 steps to 0.1 s on both backends. All 40 AmgX pressure solves used observed GPU work, with 8,040 intercepted launch API calls in total. Maximum differences from native GAMG were about 2.5×10⁻¹² m/s for velocity and 1.9×10⁻¹⁰ m²/s² for pressure. These small functional tests are not a representative speed benchmark.

The private AmgX adapter supports **serial, symmetric, noncoupled pressure systems only**. It rejects unsupported MPI/coupled cases, rebuilds its solver setup, and uses an extra factor-of-ten tolerance safety margin before checking the native OpenFOAM residual independently. Its prototype timing must not be presented as optimized AmgX performance.

A separate AmgX rotor compatibility check completed five identical adaptive steps from t=0.600 to about 0.60086186 s on the existing checksum-verified 922,576-cell warm seed, alongside a serial GAMG control. Both completed normally. All ten GPU pressure solves passed independent native stopping checks and produced 16,310 successful intercepted CUDA launch API calls. Final relative L2 differences were about 8.34×10⁻⁶ for velocity, 8.38×10⁻⁴ for pressure and 1.23×10⁻⁵ for internal flux; mean lift differed by 2.91×10⁻⁷ relative. Continuity checks passed. This is a short numerical/device compatibility check, not a speed benchmark or a new lift-study measurement.

The reviewed [AmgX source, recipes and evidence](amgx/README.md) are now included. A later [restore-only check](amgx_portable_restore_checks.json) exercised the published recipes into four fresh cavity/rotor pilot directories on this installed host, rehashed every restored input, and confirmed that the published bundle and installed libraries stayed unchanged. Those restored copies were not simulated or compiled; a new-host rebuild is still untested.

The older [Ginkgo benchmark evidence](benchmark_evidence_manifest.json) remains unchanged: the tested CUDA configuration took about 250.130 s versus 137.435 s for the faster two-rank CPU reference. That result applies to that pressure-only bridge. It does not determine the performance of the newer full-flow stdpar or SPUMA ports, or this separate AmgX adapter.

## Isolation and next gates

Installations are under task-owned prefixes in `/opt/openfoam-workspace/gpu-feasibility/`. They do not replace the Windows driver, system compiler, global shell profile or installed Foundation 14. SDKs and compiled build trees are excluded from publication; reviewed recipes, source pins, patches and test evidence are included separately from ongoing diagnosis.

This WSL driver exposes basic managed memory, but not full concurrent/pageable unified-memory features. A basic managed allocation test passed. The stdpar build therefore uses an explicit SM121 managed-memory configuration rather than the GH200 defaults. Earlier qualified small-test traces recorded CUDA API calls without kernel-activity records; the separate device-only-output test supplies stronger execution evidence for the compiler gate. The failed large-case capture contains incomplete NVTX data and no CUPTI API/activity tables, with a warning about the older collector's CUDA13.4 driver support. That unusable capture is not evidence of zero GPU execution.

A separate private **Nsight Systems 2026.5.1 CLI** is now installed and its version command passes. NVIDIA explicitly lists CUDA 13.4 support in its [release notes](https://docs.nvidia.com/nsight-systems/ReleaseNotes/index.html). The package was extracted into a new task prefix without running installation scripts or replacing the historical SDK profiler, driver, shell profile or backend default. One existing 32,768-element native Field control completed with true application/profiler/export exits zero and exact arithmetic. Its complete algebra range contains **8 successful launch API calls, 9 successful synchronization calls and 8 attributable GPU kernel records**, with successful completion after the final launch and no unsupported-driver warning. This tool update verifies genuine small-test CUDA execution; it does not repair or qualify the failed rotor time loop. The original postprocessing-only rejection of Linux's truncated process label and the reviewed audit-only correction are preserved; the GPU test ran once.

The reviewed [current profiler recipes and kernel evidence](nsight_2026_5/README.md) include a lossless restricted trace, exact installation metadata and the original audit history. Incomplete-event and disabled Unified Memory tracing warnings remain visible; full raw reports, environment tables and unrelated process metadata remain private.

The native full-size first-step failure remains unresolved after successful large-mesh startup. No additional missing runtime dependency has been identified. Native rotor timing remains prohibited until both functional GPU execution and unchanged strict numerical gates pass. Any later timing must use a controlled workload after compilation and other GPU tests are idle. No speedup or production-default adoption is claimed for the new paths.

The earlier [source-based feasibility assessment](native_stdpar/README.md) and local inventory describe the environment before these installations. Their dated observations are retained as historical evidence.
