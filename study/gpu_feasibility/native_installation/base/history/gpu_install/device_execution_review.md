# Independent stdpar device-execution review

Reviewed 2026-11-01. This is a source review and suggested validation procedure, not an executed compiler, GPU, or CFD test. It does not change the installation or production cases.

## Recommended evidence

Keep two separate smoke tests: ordinary managed-heap arithmetic to check the selected memory mode, and a device-only-output marker to establish strong runtime evidence of the GPU execution path. Where available, also retain an Nsight Systems CUDA kernel trace attributable to the smoke-test process. Compiler diagnostics, embedded GPU code, CUDA event timings, or GPU utilization alone do not establish that the tested algorithm actually ran on the GPU.

For the marker:

1. Compile and link with the intended `nvc++` and GPU-only `-stdpar=gpu`, explicit `-gpu=cc121,mem:managed` or the installed compiler's confirmed native target, and ordinary optimization. Record the exact command, compiler version, runtime libraries, CUDA device name, and capability. Do not add combined multicore/host targets or change to the distinct `gpu:acc` backend merely to make a marker work.
2. Create a sufficiently large index array on the managed heap, initialize it on the host, and verify its pointer attributes. If using ordinary `new[]` or a vector, require `cudaMemoryTypeManaged` to check allocation interception. An explicitly `cudaMallocManaged` array is a useful diagnostic alternative but does not prove interception of ordinary heap allocations.
3. Allocate a separate output with `cudaMalloc`. Check every API return and require `cudaPointerGetAttributes` to report `cudaMemoryTypeDevice`, a valid device pointer, and `hostPointer == nullptr`. If these conditions fail, do not make the device-only-access inference. Never attempt to prove the absence of host access by dereferencing this pointer on the CPU.
4. Initialize that device output to a sentinel with `cudaMemset`, then synchronize successfully. Run `std::for_each(std::execution::par_unseq, ...)` over the managed indices. Capture the device pointer and a runtime seed by value. Each iteration must write its own output element with a nonuniform unsigned-integer expression, for example `(i ^ seed) * 1664525u + 1013904223u`. Use defined unsigned overflow, no shared reduction, no CUDA API calls in the lambda, and no references to host stack objects.
5. Check CUDA errors and `cudaDeviceSynchronize`, copy output back with a checked CUDA copy, and verify every expected value plus the changed sentinel. `cudaMemcpyDefault` avoids assuming that a compiler-intercepted destination vector is ordinary host memory. Initialize/read managed host buffers only after synchronization; this matters when concurrent managed access is unavailable.
6. Compute any sequential reference into a separate host-accessible buffer. Do not run a CPU-only/fallback version against the device-only output allocation, and do not deliberately test an illegal host write. Archive the allocation attributes, exact verification counts, checksums, errors, and any profiler trace.

Successful exact writes into an allocation documented as inaccessible directly from the host are strong evidence of the device path in this test/configuration. This is not a formal proof of every generated arithmetic instruction, a speedup measurement, proof of Umpire allocation coverage, or proof that a later OpenFOAM solve is fully offloaded. Those remain separate gates. The reasoning relies on the recorded pointer attributes and this algorithm's direct output writes; it should not be generalized to different allocation modes or compiler configurations.

NVIDIA staff explicitly demonstrates C++ `par_unseq` with `acc_malloc` device pointers, and states that `cudaMalloc` device pointers are also usable; the example works with and without compiler-managed allocation enabled. This directly supports the proposed interoperability test. The CUDA runtime documents `hostPointer == nullptr` as indicating that the allocation cannot be accessed directly by the host. [NVIDIA stdpar/device-pointer discussion](https://forums.developer.nvidia.com/t/implicit-data-copy-to-device-for-allocated-arrays-using-compilation-option-stdpar-gpu/253279), [CUDA pointer attributes](https://docs.nvidia.com/cuda/cuda-runtime-api/cuda_runtime_api/group__CUDART__UNIFIED.html).

## `acc_on_device` and the reported 26.9 regression

The October 30 report is specifically an OpenACC `nvc`/`nvc++` combined-target dispatch reproducer using `-acc=gpu,multicore` or `-acc=gpu,host`, observed on an x86-64/B200 system. Its trigger combines target-dependent `acc_on_device` (or `__builtin_is_device_code`) with a compile-time dead loop. The author reports that GPU-only `-acc=gpu` succeeds. This is a user report, not an NVIDIA-confirmed diagnosis, and does not establish a regression in ordinary GPU-only C++ stdpar.

I found no primary source establishing `acc_on_device(acc_device_not_host)` as a dependable marker inside the default Thrust-backed stdpar lambda. Treat it as optional corroboration if it compiles and its behavior is separately established, not as the sole gate. Do not infer stdpar behavior from an OpenACC compute-region reproducer. Avoiding unnecessary combined-target flags and dead-code tricks is sufficient for this bounded smoke design; do not downgrade or change production settings merely because of this report. [Exact regression report](https://forums.developer.nvidia.com/t/regression-in-26-9-abort-after-gpu-kernel-launch-when-built-for-both-gpu-and-multicore/387474).

NVIDIA documents GPU-only, multicore-only, and combined stdpar targets, as well as managed and unified memory modes. Its target preprocessor macros describe what was compiled, not which path actually executed. [NVHPC user guide](https://docs.nvidia.com/hpc-sdk/compilers/hpc-compilers-user-guide/).

## Bounded alternate routes after the primary stack gate

- **SPUMA:** upstream CINECA documentation describes a full OpenFOAM GPU port for NVIDIA and AMD; its NVIDIA build uses NVHPC, CUDA and optionally CUDA-enabled Umpire, so these dependencies are reusable. Its GPU-support history explicitly lists `pimpleFoam`. This makes it a relevant next candidate, but does not validate our Foundation14 actuator wrapper, boundary conditions, or performance. Unported host functionality can introduce transfers or compatibility limitations. [Repository/build requirements](https://gitlab.hpc.cineca.it/exafoam/spuma), [primary supported-solvers record](https://gitlab.hpc.cineca.it/exafoam/spuma/-/wikis/GPU-support/diff?version_id=d5a4015670e31d8ad98646b17ed5dd017bf43969).
- **NVIDIA AMGX 2.5:** official notes add CUDA 13 and Blackwell support and detect unavailable asynchronous memory pools with a fallback. This is relevant if our environment lacks async pools, but it remains a linear-solver route requiring an adapter and a matched benchmark. The notes list SM120, not an explicit N1X/SM121 validation; do not claim measured local compatibility or speedup. [Official 2.5 release notes](https://github.com/NVIDIA/AMGX/releases/tag/v2.5.0).

Neither alternative is an instruction to launch another installation or change the running study. Establish the primary compiler/device gate first, then make an explicit bounded choice.
